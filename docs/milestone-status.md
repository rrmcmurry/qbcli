# First milestone results — October 5, 2026

The smallest read-only connection proof works on this PC. This paragraph records the first milestone; subsequent SDK work is summarized in the current command contract.

## What worked

- Independent .NET 10 solution on branch `codex/read-only-poc`, with separate CLI, Core, QuickBooks adapter and offline tests.
- Self-contained x64 distribution in `artifacts/win-x64`; run `qbcli.exe` from that folder.
- Official local QuickBooks COM request processor, read-only preference, no personal-data requirement, administrator approval, then a real company session.
- `company info`: company and legal name both returned `Test` from the user's new `QBData/Test.QBW`.
- `accounts list`: returned Payroll Expenses (Expense) and Payroll Liabilities (OtherCurrentLiability), both active. JSON and the human table agreed. These are observed responses; no independently seeded account/subaccount/inactive fixture was available.
- Published executable read both commands successfully. Three further pairs of JSON reads passed ConvertFrom-Json, expected company/count assertions and exit-code checks. Default open-company selection also returned Test.
- Verbose successful commands confirmed EndSession, CloseConnection and COM release. After authorization, later reads needed no new prompt.
- 47 offline tests passed: domain/ordering, JSON/errors/output, arguments, allowlisted XML queries, optional/required fields, XML security, malformed/partial responses, status handling, and successful/failed session cleanup.
- Unsupported `invoice create --json` returned structured `invalid_arguments` and exit code 2 before connection.
- `QBData/` is fully Git-ignored, including QuickBooks-created sidecars. No Intuit binaries are bundled.

## Unexpected difficulties

1. Intuit's documentation pages needed browser rendering; simple page retrieval produced a shell instead of the documentation.
2. Late-bound COM dispatch could not access AuthPreferences (0x80020006). A narrow binding to documented IRequestProcessor4/IAuthPreferences fixed that. Interface IDs/DISPIDs/enums were checked against the installed public type library.
3. Authorization preferences shared the processor's COM identity/RCW. Releasing preferences immediately caused InvalidComObjectException before BeginSession. Retaining the shared identity until final cleanup resolved it.
4. **User-observed authorization step:** the confirmation field did not accept `yes` until the user opened “Learn more about permissions of applications that integrate with QuickBooks.” After visiting the link, the user typed `yes` and completed approval. This is recorded in test-PC setup as a QuickBooks 2024 R21 observation.
5. Company names and account IsActive are optional in the published schema. Nullable DTO values avoid fabricating data.

## SDK limitations and practical limits

- Local Windows COM, installed/licensed QuickBooks and per-company administrator authorization are prerequisites.
- x64/x86 compatibility is a deployment boundary. Only local x64/QuickBooks 2024 R21 was exercised.
- AccountQuery's published schema has no iterator; this small query omits MaxReturned. Account-name lookup has a documented numeric-name/account-number ambiguity.
- An authorization modal can block BeginSession. There is no timeout/cancellation worker in the POC.
- JSON describes normalized query results, not a transactional snapshot across multiple reads.
- Immediate repeated success is evidence for the basic connection, not proof of unattended reliability, service hosting, or every permission/multi-user configuration.
- Full SDK 17 license and applicable commercial distribution terms still need confirmation before commercial release; current Intuit redistribution guidance prohibits bundling raw request-processor DLLs.

## Original recommendations after the connection proof

Keep the current layering and explicit COM interfaces. Before expanding: seed subaccount/inactive fixtures, verify permission denial/revocation and multi-user behavior, and add host/version diagnostics for a supported deployment matrix. A future hosted adapter should have a dedicated STA worker and explicit process/session management; do not move COM calls onto arbitrary async continuations.

Next accounting commands, after accepting this read-only baseline:

1. Customers list and vendors list, with SDK-supported completeness/pagination behavior.
2. Open invoices and open bills, with decimal amounts, currency and explicit status semantics.
3. Trial balance, once report columns/accounting basis/date semantics are normalized and totals reconciled to a seeded fixture.
4. Transaction history after defining supported transaction types and coverage.

No write operations should begin until the read-only architecture is explicitly approved. See sdk-research.md for primary sources and unresolved distribution questions.
