## Company file mode

Company sessions accept `--file-mode any|single-user|multi-user`. Default `any` maps to the SDK's `qbFileOpenDoNotCare`, single-user to `qbFileOpenSingleUser`, and multi-user to `qbFileOpenMultiUser`. This configures BeginSession before any request. It cannot switch a company already open in another mode; the SDK can reject the session. For an unopened company, DoNotCare may open single-user mode. Read [Intuit's SDK guide](https://static.developer.intuit.com/resources/QBSDK_ProGuide.pdf) for edition and open-file constraints.

The requested mode is recorded in previews, execution/query results, durable plan headers and `connection.requestedFileMode`. `connection.host.fileMode` remains the independent HostQuery observation. A resumed pending plan may request another mode but still must use the original company and protocol; confirmed writes are never replayed. Mutations still require explicit apply, path and journal. The stable full authorization profile remains the same for all modes.

This option applies to convenience reads, live capability discovery, SDK run/batch/resume and bulk reclassification. Mutation previews remain offline. Offline validation/schema/discovery, subscriptions and callback listeners reject it. Native mode mapping and startup/cleanup ordering have automated coverage. After the user reopened QuickBooks, HostQuery reported SingleUser and a new explicitly requested single-user ItemServiceMod succeeded; its new journal records that requested mode. This establishes the tested session only, not unattended mode switching or multi-user compatibility.

## SDK request effects

SDK previews, execution results, journal plan records and operation discovery distinguish four possible effects: `mutatesCompany` for accounting/list writes, `mutatesRecoveryState` for event-recovery deletion or explicit message-set recovery IDs, `mutatesSubscriptions` for installation-scoped subscription changes, and `affectsUserInterface` for ListDisplayAdd/Mod or TxnDisplayAdd/Mod. These describe plan intent, not proof changes occurred; inspect outcomes and fresh read-back. Mixed company plans can report more than one effect. All non-query operations still require explicit apply and a journal; company transport requires an explicit company path. Categorization never reduces those guards. Live display behavior remains unverified.

DataEventRecoveryInfoDel deletes recovery metadata for a SubscriberID; it does not delete the subscription itself. On a fresh owned subscription whose recovery query returned no_match, the delete returned3120/not found and remained a failure. Subsequent queries confirmed no recovery record and the subscription still present, followed by explicit owned-subscription cleanup. This verifies the empty-state negative case only; deletion of an existing recovery record and actual lost-event recovery remain unverified.

## Linked requests with SDK macros

SDK macros let later requests use IDs created earlier in the same plan. For example, put `"$attributes":{"defMacro":"TxnID:invoice_1"}` inside InvoiceAdd. A later ReceivePaymentAdd/AppliedToTxnAdd can use `"TxnID":{"$value":"","$attributes":{"useMacro":"TxnID:invoice_1"}}`. Define another TxnID macro on ReceivePaymentAdd and use it in DepositAdd/DepositLineAdd/PaymentTxnID to deposit that exact payment. Inspect each expanded schema for supported attributes; macros do not bypass field validation.

The macro name after the colon is 1..40 ASCII letters, digits, dashes or underscores. Definitions must be unique across the plan, and every use must exactly match a definition in an earlier request. Undefined/forward/same-request references and duplicate definitions fail before connecting. A single `sdk run` or `sdk validate` cannot consume a definition from another invocation.

One SDK company session serves the entire plan, so count/byte batch splitting preserves macro dependencies. Definitions expire when that session ends. This follows [Intuit's Programmer Guide, chapter12](https://static.developer.intuit.com/resources/QBSDK_ProGuide.pdf). Live tests created and freshly queried an invoice, its full payment and its deposit both in one message and in three messages in the same session; paid balance, applied/deposited links and amounts were verified. Forty-character names also passed. Other tag/defining-element combinations remain subject to SDK semantics and are not exhaustively verified.

Macro chains are not atomic. A failed definition can cause dependent failures under continueOnError within a message. The engine stops before later messages after failures, warnings or uncertain outcomes. Resume starts a new session and permits a self-contained macro chain only when every definition and use belongs to the proven-unexecuted remainder. References to definitions completed or failed in the old session are rejected; use confirmed real IDs in a new reviewed plan instead of replaying successful creates. Uncertain submissions still block apply.

TxnLineID macros were also verified on DepositAdd/CashBackInfoAdd: define `TxnID:deposit_1` on the deposit and `TxnLineID:cashback_1` on its cash-back aggregate. Later ClearedStatusMod requests can use the transaction macro alone for the main deposit posting or both macros for the cash-back posting. Both forms passed within one message and across three messages in one session. Separate GeneralLedger queries returned named ClearedStatus values and verified the two posting amounts. Changing the cash-back line to NotCleared afterward preserved the main deposit's Cleared status and both amounts. This is scoped deposit evidence, not verification of every line-defining element.

For `sdk run TransactionQuery --all`, summary identity is TxnType plus TxnID; posting identity adds TxnLineID, optional AccountRef ListID and optional invariant numeric Amount. Inventory income, asset and COGS rows can share a line identity; purchase-credit rows can also share the same account with different amounts. Missing discriminators stay null. Summary identity ignores accounts and amounts, so changed values cannot hide duplicate summaries. Equivalent numeric text cannot hide posting duplicates; malformed/duplicate amount fields fail visibly. Projections internally fetch missing AccountRef/Amount and transaction identities, removing only fields added by qbcli. Deposit, inventory sales and inventory purchase-credit fixtures matched independent unbounded queries at page size1; purchase credits retained eighteen rows across eighteen pages for full/amount/account projections. These fields are not claimed to distinguish every SDK posting context. Other iterator queries retain their existing duplicate-ID checks.

## Structured inputs

`sdk validate OPERATION --input fields.json` validates offline. `sdk run OPERATION --input fields.json` executes queries; non-query operations preview unless --apply is present. Fields use actual SDK tag names, nested aggregate objects and arrays for repetitions. Invisible OR/skip groups are flattened. A single OR accepts one alternative; repeated choices accept multiple alternatives grouped in schema order. Use `$choices` for ordered interleaving: an array of objects, each selecting exactly one documented alternative. Do not mix `$choices` with grouped fields from that same choice. Example: `{"JournalEntryAdd":{"$choices":[{"JournalDebitLine":{"AccountRef":{"FullName":"Expense"},"Amount":"1.00"}},{"JournalCreditLine":{"AccountRef":{"FullName":"Income"},"Amount":"1.00"}}]}}`.

For example, CustomerAdd fields:

```json
{"CustomerAdd":{"Name":"Fictional SDK customer"}}
```

Use decimal strings to preserve monetary precision, date strings yyyy-MM-dd and ISO date-times. Response scalar values remain strings. `$attributes` supplies documented attributes; scalar attributes use `{"$value":"VALUE","$attributes":{}}`. The engine manages requestID. Unknown fields/operations, duplicate JSON properties, invalid types, missing required values and unsupported imported country/version fields fail before connecting.

Batch plan:

```json
{
  "protocolVersion":"13.0",
  "country":"US",
  "onError":"continueOnError",
  "requests":[
    {"requestId":"1","operation":"CustomerQuery","fields":{"ActiveStatus":"All"}},
    {"requestId":"2","operation":"ClassQuery","fields":{}}
  ]
}
```

`sdk batch --input plan.json` validates the entire plan first, uses one STA connection and submits bounded message sets. Default: 50 requests and 1 MiB UTF-8 per message; --batch-size allows1..1000. Optional batch JSON `maximumBatchBytes` accepts an integer1024..16777216; these are application tuning bounds, not asserted SDK maxima. Input is limited to64 MiB and100000 requests. Each transaction still requires its own SDK request. Batching saves connection/process overhead; local synthetic timings do not establish production throughput guarantees.

Batch construction measures the nonempty envelope and each escaped UTF-8 request once, then serializes each complete message once. A local5000-request/1000-per-batch comparison produced byte-for-byte identical messages in about18 ms versus1926 ms for the previous growing-candidate algorithm. This measures serialization only, without SDK calls. Reproduce from the repository root with `dotnet run --project scripts/batch-benchmark/benchmark.csproj -c Release`; timings vary. Live48-query checks split into four messages at1024 bytes and two at2048 bytes, with all outcomes correlated. An explicit query journal is honored using --apply, --company-file and --journal; the read-only executor does not receive write intent.

`sdk run CustomerQuery --all --page-size 500` completes a supported iterator query in one session. Iterator stability, remaining count, duplicate identifiers and progress are checked. Filters retain their documented semantics: include `ActiveStatus: All` when inactive records are needed. Non-iterator queries/direct lookup branches cannot use --all. Iterator IDs cannot continue in another process/session.

## Authorization and write outcomes

Every session requests the same full read/write, personal-data and unattended profile under McMurry Software QuickBooks CLI. An administrator grants it in QuickBooks. This consistent profile follows the user's explicit request. The observed permission dialog required opening its help link before typing yes. Full-profile authorization and subsequent connections succeeded; running with QuickBooks fully shut down remains untested.

Mutations require --apply and an explicit company path. The host country/protocol and actual SDK company path are checked before submission. Agent-run destructive tests are limited to QBData/Test.QBW. A named session mutex rejects overlapping qbcli SDK sessions.

Execution returns independently correlated per-request outcomes: succeeded, no_match, warning, failed, unprocessed or unknown. Batches are non-atomic. continueOnError attempts later requests within the same message; the executor stops before subsequent messages after errors/warnings/unknown outcomes. Successful changes remain applied. Missing/malformed responses or submission exceptions are conservatively unknown; no automatic write retry occurs.

Per-request statusMessage preserves the SDK's explanation in result JSON and journals. It can contain company values and is never copied to diagnostic stderr. This exposed the date and employee-setting prerequisites for time tracking; numeric status alone did not explain them.

Applied mutations create a durable JSONL journal with the plan, submission intent, outcomes and finish record. Default artifacts/runs/UUID.jsonl, or --journal NEWFILE in an existing directory. Existing journal files are never overwritten. Journals contain accounting values and require the same protection as company exports. Automatic resume is not implemented; reconcile unknown outcomes before retrying. Typed SDK message-set recovery controls are described below.

Starting with0.8.10, new plan records also identify the originating process by PID and round-trip UTC start time. Resume observes that exact process before applying: running or an unavailable observation blocks apply before SDK connection. A reused PID with a different start time is evidence that the original process stopped. A finished journal establishes request execution outcomes, not session cleanup or process exit; cleanup can still be waiting inside COM. Preview reports sourceProcess and sourceProcessState. Older compatible journals report legacy_unknown and retain prior resume behavior plus the SDK session mutex; they cannot establish process exit from their journal alone. No client is terminated or request retried by this check.

`sdk resume --input prior.jsonl --company-file PATH` performs an offline preview of residual work. It validates a current company-scoped journal's typed plan digest and exact submitted batches, skips confirmed succeeded/no_match outcomes, excludes failed requests, and selects only never-submitted requests or requests explicitly acknowledged by SDK status3231. Submitted missing outcomes, unknown/warning outcomes and uncertain message envelopes block apply. Use `--apply` to submit eligible residual requests to the original company, in a new journal; the source is retained. Self-contained pending macro chains are permitted; references to completed/failed macro definitions and recovery-ID journals are rejected. Truncated JSONL and older journals without current transport/batch metadata are rejected. Failed requests require a separate corrected plan. No uncertain write is automatically replayed or reconciled. Live duplicate-name failure tests verified selective class resume and an entirely unexecuted invoice/payment/deposit macro chain resumed in a new session, with fresh query verification.

Batch plans now expose typed `messageSetAttributes`: responseData (includeAll/includeNone), newMessageSetID and oldMessageSetID. IDs must be nonempty, at most 23 characters, with no colon or slash. Explicit IDs require a single message set; the engine rejects splitting them across batches. Recovery controls require --apply, an explicit company path and a journal even when all contained requests are queries. They affect recovery state independently of accounting mutations; results include mutatesRecoveryState and messageSetResponses.

To clear one known completed recovery record, provide `requests:[]` and `messageSetAttributes:{"oldMessageSetID":"ID"}`. Empty requests are accepted only for this clearing form. An explicit zero SDK messageSetStatusCode is required for success. A nonzero message-set status fails the run even if request statuses report success. Missing request responses remain unknown, including status-only cached replies with envelope status zero. Journals save the exact internally generated XML before submission; arbitrary XML input remains unsupported.
