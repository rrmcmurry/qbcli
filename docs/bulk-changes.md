# Bulk changes through the documented SDK

The generic SDK batch executor, journals and a posting-line reclassification planner are implemented. There is no universal SDK command that reclassifies every posting in an account. Automatic uncertain-write reconciliation remains design work.

Selective resume is available explicitly through `sdk resume --input prior.jsonl --company-file PATH [--apply]`. It skips confirmed completions, excludes failures needing a corrected plan, and submits only requests proven never executed. Any uncertain submission blocks apply. See [SDK command contract](sdk-commands.md) for the exact journal requirements and macro/recovery limitations. Automatic uncertain-write reconciliation and replay remain unimplemented.

Use `qbcli bulk reclassify --input selection.json --company-file C:\\Test\\Test.QBW` for preview. The input is `{"accountId":"SDK ListID","classId":"SDK ListID"}` with an optional `transactionTypes` array selecting Check, Bill, CreditCardCharge, CreditCardCredit, VendorCredit, ItemReceipt, JournalEntry and Deposit. Omission selects all eight. The command resolves active references in the selected company, completes each selected type's iterator with line detail, and selects blank-class expense, journal debit/credit or deposit source-account lines with the exact account ListID. It does not include subaccounts. Purchase item lines, deposit cash back and header/destination postings are outside this planner's scope; opt-in service-item sales support is described below; output always reports `coverageCompleteForAllAccountPostings:false`. Scanning every selected type avoids relying on account filters whose header/line interpretation could omit eligible lines. Missing posting-account ListIDs abort planning instead of silently excluding unidentified lines.

Add `--apply` to generate a fresh plan from current reads and execute it with optimistic EditSequence checks, a durable journal, one session and bounded batches. `--page-size` and `--batch-size` default to 500 and 50. The preview includes original record snapshots, selected line IDs, counts, typed SDK plan and digest. Apply recomputes the selection; it does not consume or promise to execute a previously saved preview. A stale EditSequence fails visibly without an automatic retry.

The planner retains **every expense line**, carrying existing class references and replacing only eligible blank classes. Live testing established that submitting only changed expense lines removes omitted expense lines, despite the reference's wording about individual modifications. Do not use a sparse expense-line list to preserve the other lines. Item lines are not submitted for modification. After submission, fresh direct queries verify each successfully changed class and compare all other returned record fields, excluding only TimeModified, EditSequence and the selected ClassRef changes. A missing record, verification mismatch or verification communication error fails the command while retaining its execution result and journal path. Verification findings are appended to the journal. This is verification after mutation, not rollback.

Journal entries retain every debit and credit TxnLineID in a single JournalLineMod list, carrying existing class identities and changing only eligible blanks. The planner omits amounts, account references and JournalLineType from modifiers so it does not rewrite those fields. Fresh verification compares line sides, amounts, entities, billable status, memos and all other returned fields. A live fixture changed40 classes across20 balanced journals, including selected lines on both sides, preserved all six lines per journal, and found no work on repeat selection. A subsequent mixed fixture also exercised the six expense transaction types in the same selection; sanitized results appear in capabilities. This does not claim coverage of every journal configuration or other-country tax fields.

Deposits retain every DepositLineRet TxnLineID in DepositLineMod, including payment-linked and preclassified lines, and carry unchanged AccountRef identities plus existing/new ClassRef values. This selects the documented account-line choice while addressing existing lines by their SDK identities. The planner does not send PaymentTxnID: live re-submission of an already deposited source returned3210. Existing-line updates preserved the original TxnID payment links, six lines per deposit, cash-back details and all other returned fields. A ten-deposit fixture changed20 direct-line classes followed by10 linked-payment classes, with fresh received-payment queries also confirming source fields unchanged (except SDK edit/time metadata). Repeated selections were empty. These are specific US/protocol13 observations; generic PaymentTxnID/OverrideClassRef remain callable documented fields for other deposit operations, not this preservation recipe.

The SDK supports multiple requests in a message set and multiple message sets in a company session. Reuse one STA session, combine changes belonging to the same transaction into one modification request, and submit bounded batches. QuickBooks still processes individual modifications internally; batching removes repeated executable/connection overhead and enables sustained work. Measure throughput before promising a duration. Bound both request count and XML bytes; these are application tuning parameters, not asserted SDK maxima.

For “all postings in account X without a class to RentalA,” resolve account and class ListIDs, enumerate every candidate page with transaction line detail, and determine blank class at the correct transaction/line level. A class present elsewhere on the transaction must not exclude eligible lines or be overwritten. Each transaction type has different modification and line-preservation semantics; do not treat partial line lists as safe without checking its schema. Report unsupported types/fields, closed-period restrictions and other exclusions explicitly.

Produce an immutable plan with company identity, target ListIDs, selection criteria, TxnIDs, line IDs, EditSequences, original and proposed values, exclusions, counts and a content digest. Preview is local validation, not a server-side dry run. Re-read/revalidate before applying; edit conflicts require a fresh plan rather than overwriting newer edits.

Persist each batch's intent before sending. Assign stable requestIDs and record every outcome independently: pending, submitted, succeeded, failed, unprocessed or unknown. A missing response or interrupted connection after submission means unknown, not failed. Checkpoint between batches; resume skips verified successes. Unknown writes require reconciliation or the SDK's documented message-set recovery mechanisms before any retry. Do not assume arbitrary SDK writes are idempotent.

stopOnError preserves prior successes and leaves later requests unprocessed (3231). continueOnError attempts remaining requests. Neither makes a batch atomic or rolls it back. The apply command stops before subsequent batches after a batch containing errors and produce a durable summary of completed, failed and uncertain work. Reversal would be a separate newly validated plan, not a guaranteed rollback.

Do not parallelize COM writes across processes to chase speed. Keep one STA worker, configurable batch sizes and progress/checkpoint output. Bulk recovery tests must cover out-of-order responses, duplicate/missing requestIDs, stale EditSequences, partial success, process interruption, unknown submission outcomes and recovery without duplicate changes.

Current sdk run/batch supports schema-validated mutations with explicit apply intent. A live CheckMod changed one expense line class to RentalA while preserving its amount and account. Live duplicate-name failure followed by successful ClassAdd verified continueOnError partial success. Journals and response correlation have offline failure tests. Arbitrary XML, automatic uncertain-write reconciliation and universal posting coverage are not implemented. Sanitized bulk test results appear in capabilities; a local synthetic measurement does not establish production throughput.

Starting with0.8.12, bulk reclassify accepts Invoice, SalesReceipt and CreditMemo explicitly in transactionTypes. The default remains the eight expense/journal/deposit types. For sales, it completes form queries, an all-active/inactive ItemServiceQuery and actual posting queries before planning. A changed transaction must have service items and one matching account/amount posting for every retained leaf; missing/ambiguous joins or unsupported retained items abort the plan before writes. All original flat/group identities, actual accounts and existing classes are retained. Target classes are assigned only to blank-class leaves on the exact selected account. Posting records are indexed once per transaction and line to avoid a full posting scan for each transaction.
